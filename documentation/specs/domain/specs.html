Projection Specification

Updated to match the current implementation in apps/projection/src and packages/models/src.

Purpose

The projection module builds projections from canonical receipts and canonical bank transactions. It owns candidate scoring, merchant-transaction projection, rule-based label suggestions, spend mix aggregation, and the merchant transaction read model used by the dashboard.

Scope Boundaries

  • In scope: candidate matching, best-match selection, merchant projection, rule-based labels, spend-mix read, and merchant-transaction read.
  • Out of scope in the current code: reseller entities, forecasting, manual override UI, historical decision log, and asynchronous projection workers.

HTTP Contract

Route Method Purpose
/projection/charts/spend-mix GET Return aggregated spend by active label or Unlabeled.
/projection/merchant-transactions GET Return the compact merchant transaction table rows.
/projection/receipts POST Rebuild the projection scope affected by one receipt.
/projection/statements POST Rebuild the projection scope affected by one imported statement.

Canonical Facts and Projections

Layer Tables Notes
Canonical facts receipt, statement_import, bank_transaction Written by scan and bank modules.
Persisted projections reconciliation_candidate, bank_transaction_receipt, merchant, merchant_transaction, label, label_assignment Rebuilt from canonical facts by the projection module.

Matching Strategy

Canonical receipts + canonical bank transactions
  -> build candidate computations per receipt
  -> filter by currency and posted-on date
  -> score by exact amount, merchant similarity, and day distance
  -> select one best match per receipt
  -> persist best_match and other_match candidate records
  -> project merchant transactions as reconciled / ambiguous / receipt_only / bank_only / cash

The current matching logic is heuristic, not ML-driven.

Labeling Strategy

Labeling is currently rule-based. The service owns a fixed catalog and suggests labels from merchant and bank keywords such as spotify, boots, caffe, tesco, uber, and amazon.

Automatic suggestions are persisted with source rule or bank_suggestion. The storage model supports user assignments, but there is no UI flow in the current repo to create them.

Current Limitations

  • No reseller table or reseller-specific read model.
  • No forecast or trend projection tables.
  • No manual match review or decision history.
  • No background job or event bus; recalculation is synchronous.
  • No direct dashboard-side write actions for labels or corrections.
